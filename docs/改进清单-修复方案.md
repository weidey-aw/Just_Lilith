## 1. T1：MOD 设置窗口被挡住 / 关不掉（A / P1）

### 根因（有证据）

游戏窗口是个**比屏幕还高的桌宠分层窗口**——`ChatPanelPlacement` 的注释里已经写明：
`rect=(480,-120 960x1200)`，底边贴屏幕底、顶边在屏幕外。
我们的 MOD 页是 `_uiRoot` 画布的子节点，位置按**画布中心**算（`ModSettingsWindow.Build()` 里
`anchorMin=anchorMax=(0.5,0.5)`、`anchoredPosition=Vector2.zero`），而画布 = 窗口客户区
→ **页面中心 = 窗口中心**，比屏幕中心高 60px 以上；页面 980×800，顶部（含右上角「关闭」）就会落到屏幕外。

补充诱因（同样会导致点不动）：

- `TransparentWindowNew` 有 `clickThrough` / `forceClickThrough` / `AutoFullPassThroughOnGaming`，
  当游戏判定「光标不在角色身上」或「正在玩别的游戏」时窗口整体穿透 → 面板收不到点击；
  我们目前对 `TransparentWindowNew` 只有键盘租约（`GameKeyboardInputBridge`），没有点击相关处理。

### 方案

1. **按桌面可视区居中 + 夹紧**（主修）
   - 复用 `ChatPanelPlacement` 已经用通的那条链路（`ChatPanelPlacement.cs` 的
     `LilithWindow.CharacterWorkArea` 静态属性 + `LilithWindow.DesktopToUnityScreen(x, y)` 静态方法，
     见 `TryClampToVisibleArea`）：
     把「桌面工作区」换算成 Unity 屏幕坐标，再把 MOD 页的矩形夹进去。
   - 抽出共用小工具 `Unity/Ui/WindowWorkArea.cs`（新）：`TryGetVisibleRect(out Rect)` + `Clamp(RectTransform, RectTransform canvas)`。
     `ChatPanelPlacement` 暂不动，避免回归；等 T1 验收完再考虑合并。
   - `ModSettingsWindow`：`Open()` 时按可视区居中（不再用画布中心）；`MaintainDrag()` 的夹紧从「画布矩形」
     换成「可视区矩形」；打开期间每 0.3s 复夹一次（窗口被拖走/分辨率变化时不会再次跑出屏幕）。
2. **保底关闭入口**（防呆）
   - 底部工具条（「打开配置目录 / 重新载入」那一行）再加一个「关闭」，即使顶部被裁掉也能关。
   - `Esc` 已有；再确认输入框获得焦点时 `Esc` 不会吞掉关闭（当前逻辑是 `!AnyFieldFocused()` 才关，保持）。
3. **穿透兜底**（复现了再做，默认不做）
   - 页面打开期间把 `TransparentWindowNew.forceClickThrough` 压成 `false`，关闭时还原；
     每帧检查一次（游戏会覆盖这个字段）。日志加 `event=clickthrough_hold`。
   - 只在观测到 `forceClickThrough==true` 或 `AutoFullPassThroughOnGaming` 生效时才压，避免误伤「玩别的游戏时不抢点击」。

### 风险

- 桌面工作区在不同 DPI / 多显示器下有偏移：`DesktopToUnityScreen` 是游戏自己的换算，我们照抄它的输入口径
  （桌面像素、左上原点）即可，不要自己再算一遍 DPI。
- 每 0.3s 复夹可能与用户手动拖动冲突 → 拖动中跳过复夹（`_dragging==true` 直接 return）。

### 验收

1. 把角色拖到屏幕四个角，各开一次 MOD 页：**整块面板（含「关闭」按钮）都在屏幕可视区内**。
2. 面板拖到屏幕外松手：自动弹回可视区内。
3. 屏幕外沿 100% 缩放下重复一次；`Esc` 与底部「关闭」都能关。

## 3. T3：窥屏不触发 + 权重要求（B / P2）

### 根因（两条，都有日志证据）

**① 视觉模型没配 → 窥屏永远走不通（这是「权重 1000 也不触发」的直接原因）**

```
event=skipped; source=screen; reason=peek_unavailable     ← 连着 5 次
配置文件： "visionProfileId": ""                          ← 视觉模型为空
```
`CanPeek()` 的第一个判断就是 `!Sources.Screen || string.IsNullOrWhiteSpace(VisionProfileId)` → false。
权重确实生效了（`PickSource` 选了 screen），但走到 `CanPeek` 就退化成普通话题，日志里只有一行 `peek_unavailable`，
**看不出到底是「没配视觉模型」还是「最小间隔没到」还是「今天次数用完」**。

**② 额度打满后整条链路停摆，只有用户说话才重置**

```
event=roll; count=3; cap=3; reason=cap_reached      ← 连着 8 次
```
`ProactiveChatService._count` 只在 `NotifyUserMessage()`（用户发消息）里清零。
所以**用户只看不说话**（桌宠场景的常态）时，主动对话最多 3 条就彻底停，窥屏自然再也不会出现。

### 方案

1. **把 `CanPeek` 的拒绝原因写进日志**（1 行改动，先把证据补齐）
   - 返回枚举而不是 bool：`vision_unconfigured` / `source_screen_off` / `min_interval(剩余 Ns)` / `daily_cap(N/上限)`。
   - `CueAndDeliver` 里记 `reason=peek_unavailable:<具体原因>`。
2. **权重语义改成 0–1000 = 概率**（按清单里的建议）
   - 现在：`p = W_screen / (W_idle + W_screen)`；1000 时约 94%，仍可能抽到闲聊。
   - 改成：`p = clamp(W_screen / 1000, 0, 1)`，**1000 = 每轮都窥屏**（受硬上限约束）。
     `idleChat` 权重保留原意（作为「没抽到窥屏时的兜底」是否开启 / 权重不影响概率）。
   - `ProactiveSettings.Validate()` 里 `Weights.Screen` 仍是 0–1000，语义注释改掉；MOD 页文案同步改成
     「权重（0–1000，1000 = 每轮都窥屏）」。
3. **额度策略**（需要你拍板，见第 8 节）
   - 方案 A（推荐）：把 `maxPerUserMessage` 解释成「一次对话爆发里最多几条」，**用户静默超过 `2 × targetIntervalSeconds`
     就把 `_count` 清零**（相当于「她安静太久之后又能主动开口」）。
   - 方案 B：新增独立设置 `maxPerHour`（滚动 1 小时），`maxPerUserMessage` 保持不变。
   - 方案 C：不改语义，只在页面状态行显示「额度已用 3/3，等你说话才恢复」——只治可见性，不治行为。
4. **MOD 页加「现在试一次窥屏」按钮**
   - 复用 `BeginPeek(..., test:true)` 那条路径（绕过兴趣与权重，但**不绕过**视觉配置与硬上限，避免滥用）。
   - 点了没反应时，状态行直接给原因（“视觉模型未配置，去‘模型 / API’里选一个 profile”）。
   - 这一步能让用户自己验证视觉链路，是 T3 的关键止血点。

### 风险

- 权重语义变化会改变现有手感（1000 从 94% 变 100%）：配置里存档的旧权重含义变了，需要在页面上写清楚；
  默认值（30）从「30/(60+30)=33%」变成「3%」——**默认值要一起调**（建议 `screen=300` 让默认仍约 30%）。
- 「额度清零」是行为变更，需要你选 A/B/C。

### 验收

1. 不配视觉模型、权重 1000、主动对话开：日志出现 `peek_unavailable:vision_unconfigured`，页面状态行给出提示。
2. 配好视觉模型后点「现在试一次窥屏」：能出图 → 转述 → 一句台词（或明确写出失败原因）。
3. 权重 1000 时，每一轮主动都由窥屏发起（次数受硬上限）。
4. 静默 10 分钟不发言：主动对话不会永久停在 `cap_reached`。

## 4. T5：用游戏自带的前台感知触发窥屏（B / P2）

### 根因

`Game/ProactiveContextProbe.cs` 的 `ReadForeground()` 用 `FindStatic(type, "IsGaming")` / `FindStatic(type, "Loose")`
去取**静态属性**，但 interop 里游戏给的是**静态方法**：

```
public unsafe static bool IsGaming()          ← 方法
public unsafe static string Loose(string s)   ← 方法
public unsafe static float GamingElapsedSeconds ← 属性（只有这个是属性）
```

日志印证：`state=foreground_probe; gaming=0; loose=0; elapsed=1` —— 前两个一直是 0（取不到），
所以「用户状态加成」里的 gaming/browsing 从来没生效过。

### 方案

1. **修探针**（先做，1 小时内可验证）
   - `IsGaming()`、`ForegroundLooseCached()`、`ForegroundLowerCached()`、`IsCompetitiveGame()`、
     `ForegroundIsVideoPlayer()` 全部按 `MethodInfo` 取并调用（`GetMethod` 而不是 `GetProperty`）。
   - 探针结果扩成：`ActivityCategory`（`gaming` / `video` / `browsing` / `coding` / `unknown`）+ 原始前台名。
   - **一次性观测日志**：`event=foreground; loose=...; lower=...; gaming=0; video=0`，
     用来确认游戏对「浏览器 / VS Code / IDEA」这些进程 `Loose()` 到底返回什么词。
     清单里说的「写代码（有检测）」需要这一步确认；如果游戏**没有**代码编辑器分类，就退到我们自己的
     进程名白名单（只读进程名，不读窗口标题，和现有隐私口径一致）。
2. **活动变化 → 延迟一次性窥屏**（按清单的调整意见）
   - 状态机：`_category`、`_categorySinceUtc`、`_activityPeekDueUtc`、`_activityPeekConsumed`。
   - 规则：类别从「非活动」切到 `gaming/video/browsing/coding` 且**持续 ≥ 10s** → 预约 `now + 20s` 的一次窥屏；
     到点时若 `sources.screen` 开启 + 视觉已配置 + 硬上限允许 + 闸门通过 → 直接 `BeginPeek(..., test:false)`，
     **不看权重、不看兴趣、不看 `maxPerUserMessage`**；同一类别只触发一次（同类再来要间隔 ≥ 30 分钟）。
   - 只切到「活动类别」才算，切回桌面/无前台不算。
3. 与 T3 的关系：T3 管「主动对话顺带窥屏」，T5 管「用户换了活动 → 立刻看一眼」，两条互斥触发（同一时刻只跑一条）。

### 风险

- 类别映射依赖游戏自己的词表，必须先用观测日志确认，不能拍脑袋写死；
- 别把 `gaming` 判成「用户在我窗口外玩别的游戏」→ 那时窗口可能是全穿透状态（`AutoFullPassThroughOnGaming`），
  窥屏照常截屏即可，但要**避免一次连发多条**（加 30 分钟同类别冷却）。
- 截屏含用户桌面：现有隐私口径不变（不落盘原始图、只留文字场景记忆、提示过隐私说明）。

### 验收

1. 打开浏览器并保持前台 30s：日志出现 `category=browsing`，约 20s 后出现 `event=peek`（或 `degraded:vision_unconfigured`）。
2. 切到桌面：不触发。
3. 同一类别 30 分钟内不重复触发；换类别可以再触发一次。
4. 权重设 0、窥屏开关开：活动触发的窥屏仍然发生（证明不受权重影响）。

## 5. T2：TTS 断句（B / P2）

### 根因

`Speech/SpeechSplitSynthesizer.cs`：

- `SplitLongSegment()`（`:88`）只在**超过 56 可读字**时才切，切点只认 `。！？；`；
- `HardSplit()`（`:135`）在 `[max-8, max]` 这 8 个字里找 `，、；：`，**找不到就按第 56 个字硬切**；
- 首段更狠：`MainThreadSpeechController.FirstChunkMaxSpeakable = 22`（`:25`、调用点 `:414`），
  `TryCutHead()`（`:417`）同样只在 `[14, 22]` 里找标点，找不到硬切。

中文台词常见「一句里只有一个逗号，逗号在 10 字处，后面 40 字没有标点」→ 三条路径都只能硬切，
听感就是「一句话被劈开」。

### 方案

1. **统一成一个切点选择函数**（替换 `HardSplit` / `SplitLongSegment` / `TryCutHead` 里的重复逻辑）
   - 按优先级记录**最后一个**合法切点：`。！？!?`（强）> `；;：:`（中）> `，、,`（弱）> 空格；
   - 约束：切出的前半段 ≥ `max(8, 40% × max)`（避免切出「好」这种两字段），后半段同理；
   - 同等优先级取**最靠后**的（让每段尽量长，少切几刀）；
   - 找不到就退到硬切（保持现状兜底）。
   - 可选增强：记录 `“…”` 引号深度，优先在引号外切；引号内没有切点时才硬切。
2. **首段策略保持不变**（22 字先出声是为「早点有声音」的既有取舍），但切点改成上面的规则。
3. **合并短段**：`CoalesceShortChunks()` 的阈值从 ≤3 提到 ≤6，且只合并**同一句内**的碎片。
4. **落日志（清单明确要求）**
   - `module=TTS; event=speech_text; text=<整段台词>`（角色台词原文）
   - `module=TTS; event=split; chars=N; chunks=k; first=22; each=[len|尾部标点|前 20 字]`
   - 挂在 `MainThreadSpeechController.BeginSequence()`（`:409`，切完片就有结果）。
   - 开关：`FoundationOptions` 加 `ui.log_speech_text`（默认 true，便于取证；想关可以关）。

### 风险

- 切点变少变长 → 每段变长，首声延迟可能变大：用「首段仍按 22 字 + 优先弱切点」压住；
  必要时首段允许放宽到 `max-8` 之外的标点（首段优先级：任何标点 > 硬切）。
- 逐段对齐（气泡文字跟语音走）依赖切片数：段数变化属正常，但需回归「气泡逐段出现」不重不漏。
- 日志含台词原文：写进 `BepInEx\LogOutput.log`（本地文件，每次启动重建），加开关可关。

### 验收

1. 造一句 40+ 字、只有 1–2 个逗号的台词：日志 `event=split` 里每段都以标点结尾（除末段），无「切在词中」。
2. 听感：一句内的停顿是「逗号级」，不是「四字一断」。
3. 逐段气泡与语音仍对齐；首声延迟不明显变差（对比 `event=tts` 的时间戳）。

## 6. T4：主动对话老是复读同一个话题（B / P2）

### 根因

- `ProactiveGenerator.BuildIdleChatInstruction()` 明确写着「**把之前没说完的话题轻轻接下去**」→ 引导复读；
- 系统对「上一轮主动说过什么」**一无所知**：`SendProactive()` 只回 `bool ok`，正文不落到任何地方
  （注释写明「不调 `_view.SetReply`」）；
- 于是每轮都拿同一份会话上下文 + 同一句指令去生成 → 话题自然收敛到同一个。

### 方案

1. **拿到主动发言的正文**（最小改动）
   - `SendProactive(instruction, onDone, tag)` 增加可选 `Action<string?>? onReply`；
     `LlmConfigurationController` 在解析出 `parsed.Text` 的地方回调（`:307` 附近那段逻辑旁边）。
2. **记忆最近几次主动发言**
   - `ProactiveChatService` 维护环形缓冲 `_recentProactive`（最近 5 条：正文摘要 ≤ 40 字 + 来源 + 时间）。
   - 重启后要不要延续：二期可选，从 `ActiveConversationWorkspaceStore.AppendAmbientTurn` 的历史里回读。
3. **写进指令（两条硬约束）**
   - 「你最近已经主动聊过：①… ②… ③…。**这次不要重复这些话题，也不要顺着它们往下续**，换一个方向。」
   - 「如果实在没有新话题，就直接问她一个具体的小问题（今天在做什么 / 刚才那件事后来怎样）。」
4. **话题形状轮换**（防止换个说法还是同一个味道）
   - 4 类形状：`关心` / `提问` / `分享自己的一点小事` / `吐槽或感慨`；取「最近 2 轮没用过的」里随机一个，
     以一句话的形式写进系统指令（仍然由模型自然表达，不给固定模板）。
5. 指令正文去掉「把之前没说完的话题接下去」这句（这正是复读的来源）。

### 风险

- 让模型「换个方向」可能变成生硬跳跃：用「形状轮换 + 只列关键词不复述全文」控制。
- 取不到正文时（`onReply` 为 null / 生成失败）不写缓冲，退化为当前行为（不能因为拿不到就崩）。
- 每轮指令变长 ~60 字，对 token 影响可忽略。

### 验收

1. 连续触发 5 次主动对话（`testMode` 或调低间隔），日志 `event=delivered` 后面带 `topic_shape=...`，
   **相邻两次形状不同**，正文话题不重复。
2. 手动把「最近聊过」塞成 3 条相同内容，生成结果应明显换话题。
3. 中途用户插一句话，`NotifyUserMessage` 后缓冲不清空（继续避免重复），但话题形状重置。

## 7. 额外发现（清单外，但和 T3/T5 观感强相关）

1. **主动对话额度只在用户发言时重置**（见 T3 ②）——这是「窥屏/主动不明显」的最大功臣，
   建议和 T3 一起改，否则 T3 的权重调好了也看不到效果。
2. **`_peeking` 没有独立看门狗**：`BeginPeek` 靠 `TranscribeScreen(..., 20s, ...)` 的 20s 超时回收；
   如果视觉请求卡死不回调，`_peeking` 会一直是 true，`Tick()` 每拍直接 return（`ProactiveChatService.cs:195`）→
   主动对话整体停摆且日志无输出。建议加：`_peeking` 超过 30s 强制复位并记
   `event=peek_watchdog_reset`。
3. **窥屏失败也消耗「最小间隔」**：`_lastPeekAtUtc` 在请求前就写了（`:402`），
   失败后要等满 5 分钟才能再试。建议改成「成功才算数」，失败只记一次轻惩罚（如 30s）。
