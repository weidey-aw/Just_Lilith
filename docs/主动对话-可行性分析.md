# 主动对话 + TTS 流水线：可行性分析

> 范围：对需求文档《主动对话》做实现可行性评估，并回答"语音合成能否用消息队列提速"。
> 本文只做分析与取舍，不含代码改动。仓库现状以 `D:\Code\Just_Lilith`（0.3.0 裁剪版源码）为准，
> 原版参考以 `_decomp/`（从 `0.3.0-ext.60` 反编译，共 601 个文件）与游戏本体 `Assembly-CSharp` 的公开 API 为准。

---

## 一、结论摘要

| 需求块 | 结论 | 难度 | 主要风险 |
| --- | --- | --- | --- |
| 主动对话骨架（开关、30s tick、兴趣值、间隔、暂存、优先级、单生成锁） | **可以做，纯新增代码** | 中 | 兴趣值手感需要真机调参；"上限衰减"按规格原样实现不生效（见 3.1） |
| 由头：闲聊（沿用当前上下文） | **可以做** | 低 | 无 |
| 由头：音乐播放 | 可以做（两条路径，见 3.6） | 中 | 游戏 `MusicPlayerController` 没有公开"正在播放"属性，需反射私有字段 |
| 由头：屏幕内容（窥屏） | **建议降级**（不要截屏 + 视觉模型） | 高 | 隐私、成本、延迟、模型能力都不划算 |
| 用户状态感知（挂机/冲浪/工作/游戏） | **可做，且比规格更轻**——游戏本体已有 `GameForegroundDetector` | 低–中 | 规格里的"键鼠量+游戏键占比"精度价值不大 |
| 到点提醒（闹钟） | **需要你拍板**（与"总开关关闭后不主动说话""剧情播放完全跳过"两条冲突） | 低（读游戏接口）| 语义冲突，不是技术难点 |
| 系统旁白不进用户消息 | **可以做，但要动数据结构** | 中 | 现有 `ConversationTurn(User, Assistant)` 是成对结构 |
| 生成与表现（同一条管线、思考中、失败静默） | **可以做**，复用 `_chatBusy` 单锁 | 低–中 | 需要新增"无用户输入"的发送入口 |
| 设置页（三组开关） | 可以做，但工作量大 | 中 | 现有设置页是反射注入原生行，每行 60–120 行样板 |
| TTS 提速（消息队列） | **队列本身不省时间，预取（流水线）才省** | 中 | 服务端是串行推理，并行无用，深度只能 1 |

**一句话结论**：这份需求 80% 是"新增一个服务 + 少量数据结构改动"，没有真正做不动的点；
需要你拍板的是 4 件事：**提醒与总开关的关系**、**屏幕由头降级到什么程度**、**用户状态感知做到哪一档**、**兴趣值"越来越难"要不要改算法**（按原规格不生效，见 3.1）。

### 2.2 游戏本体直接给出的 API（不需要自己写 Win32 轮询）

这些都在 `Assembly-CSharp` 里，插件此前已用反射/Interop 访问同类 API（例如 `WindowsNativeAPI.GetAsyncKeyState` 用于 F7 热键）：

| 需求 | 游戏 API | 说明 |
| --- | --- | --- |

### 2.3 原版 `0.3.0-ext.60` 里已经有一套主动对话（但设计不同）

反编译结果（`_decomp/unity/`）：

| 文件 | 行数 | 作用 |
| --- | --- | --- |
| `AmbientChatService.cs` | 3706 | 主动对话主服务：事件池、预合成、剧情边界回调、硬件空闲判定、口型驱动 |
| `AmbientEventPool.cs` | 585 | "由头"池，持久化到 `BepInEx/plugins/Just_Lilith/ambient/events.json` |

`ambient_min_interval_seconds=300`、`ambient_max_per_day=3..5`、`ambient_idle_required_seconds=180`、
`ambient_synthesize_delay_seconds=90`、`story_callbacks`、`ambient_profile`。

**结论：原版是"事件池 + 预生成 + 预合成音频 + 剧情边界回调"，和你这份规格（兴趣值 + 暂存队列 + 加权随机）是两套设计。**

1. **预合成**：`SynthesizeAndStoreAsync` + `EventAudioReady` 门控——由头台词提前合成好，轮到时立刻出声，这是主动对话"即时感"的关键（也正好回答第七节的 TTS 问题）。
2. **硬件空闲判定**：`HardwareIdleEnough`、`NoHardwareInputSinceOpener`——用 `GetLastInputInfo`，不做键位采样。
3. **剧情边界**：`TryQueueStoryCallback` + 边界标记，避免和剧情抢话。

## 三、需求逐条评估

### 3.1 兴趣值模型（1.4）——可做，需要一次数值反推

规格本身是自洽的：`0..100`、`≤50` 不触发、`>50` 时按
`clamp((兴趣 + 状态修正 − 50)/50, 0, 1)` 触发、生成即清零并降上限、用户发消息重置。

**唯一需要计算的是"期望间隔 → 每轮增量"**。规格要求用数值方法，实现上很轻：

```
给定：检查周期 T=30s，期望间隔 D（默认 300s），最大次数 N=3
每轮增量 Δ ~ U(a, 2a)（均值 1.5a）
上限 C 初始 100，第 k 次触发后 C ← max(50, C − 50/N)

求 a：模拟/解析出"从 0 开始到首次触发"的期望轮数 ≈ D/T − 1（留一轮给状态修正）
用二分法在 a∈[0.1, 30] 上求解，置信区间用 1e5 次蒙特卡洛校验
```

实测（本次用蒙特卡洛验证过，6000–8000 次，增量 `U(a,2a)`、无状态修正）：

| 每轮增量均值 | 首次触发平均轮数 | ≈ 时间 |
| --- | --- | --- |
| 3 点 | 21.5 轮 | 645s |
| 5.25 点 | 13.1 轮 | 392s |
| **7.2 点（a≈4.8，即 5–10 点区间）** | **9.6 轮** | **287s** |
| 7.5 点 | 9.6 轮 | 287s |

所以默认值应为 **增量 `U(4.8, 9.6)`（约 5–10 点/轮）**，而不是 3–4 点；这与规格里写的"5–10 点"一致。
建议程序里保留二分法求解，用户改"期望间隔"后自动重算，并在设置页回显"每轮增长约 X–Y 点 / 约 N 分钟会开口一次"。

**⚠️ 规格里"兴趣上限下降 50/最大次数"这条，按原样实现不会产生"越来越难"的效果。**
因为触发概率是 `(兴趣−50)/50`，而兴趣每次触发都清零、再爬回 50 附近就掷骰，
上限从 100 降到 83/66/50 时，概率区间反而几乎碰不到上限。模拟结果（a=4.8，三次触发间隔）：

| 衰减方式 | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 规格原样（只降上限） | 298s | 297s | 298s |
| **建议：概率再乘 `(N−次数)/N`** | 298s | 319s | 374s |

建议二选一（或都留成配置）：
1. 概率乘以剩余次数比例 `max(0.15, (N−count)/N)`（改动一行，效果即上表）；
2. 或者让"每轮增量"随次数衰减（第二次起乘 0.7）。

否则验收场景 2 里"后面越来越难触发"会变成"三次间隔一样"，属于**规格缺陷**而非实现问题。

**注意两个实现细节：**

- 状态修正可能让概率长期为 0（例如挂机 −15 且兴趣 60 → 概率 −0.1 → 0），此时**不应清零兴趣**（规格说"没生成由头不消耗"），要区分"没触发"和"触发但没生成"。
- 触发概率是每轮独立掷骰，实际间隔方差较大。若用户嫌"有时太快"，可把概率改成 `P = (I−50)/50` 的平方（更保守），这属于手感参数，建议留成配置。

### 3.2 由头、暂存与优先级（1.2、1.5）——可做，是纯状态机

```
每 30s：
  if 剧情播放中: return                                  # 优先级 0
  if 到点提醒命中: 投放(提醒); return                      # 优先级 1（需先定总开关语义）
  if !总开关: return
  处理外部请求队列（P1）
  清理过期暂存 → 按优先级尝试投放 1 个 → 若成功 return
  if 兴趣掷骰命中:
     生成由头 → 尝试投放；投不进去（用户输入中/对话中/语音播放中/生成锁被占）→ 暂存
```

"投不进去"的判定全部现成：

| 判定 | 现有信号 |
| --- | --- |
| 用户正在输入 | `LlmConfigurationView._chatInput.isFocused`（或 `AnySettingsFieldFocused`） |
| 正在对话/生成 | `LlmConfigurationController._chatBusy`、`DialogueManager.IsBusy` |
| 正在说话/排队 | `MainThreadSpeechController.SpeechActive`、`LlmGameBridge.IsConversationActive` |
| 气泡未清 | `LlmGameBridge` 的 `_bubbleQueue.Count`（已有 `IsConversationActive`） |

暂存队列建议就地保存（内存 + 可选落盘），带 `expiresAt`、`weight`、`source`、`narration` 四个字段即可。

### 3.3 生成、历史与记忆（1.6）——**这里有一个结构冲突，需要决策**

现状：`ConversationContextBuilder.BuildRecent(session, input)` **总是**把 `input` 追加成 `ChatRole.User`；
而 `ConversationTurn` 只有 `User`/`Assistant` 两个字段。所以"只插入系统旁白、不插入用户消息"有两种落地方式：

| 方案 | 做法 | 影响 |
| --- | --- | --- |
| **A. 旁白当特殊 user 消息**（推荐 MVP） | 发送时用 `BuildRecent` 的变体，把旁白包装成 `【环境旁白｜<来源>】…` 作为 user 输入；成功后**只持久化 Assistant**，历史里不留这一轮 | 需要 `ConversationTurn` 允许 `User=null` 或新增 `bool IsAmbient`；旧历史兼容成本低 |
| B. 扩展会话结构 | 给 `ConversationTurn` 加 `Kind`（User/Proactive/System），上下文构建按 Kind 渲染 | 干净，但要改 store、序列化、迁移（`SchemaVersion` 从 3 升到 4） |

**建议**：MVP 用 A，并在 `OrdinaryChatOutput`/turn 上打 `ambient=true` 标记，这样：
- 统计"用户说过的话"时跳过（规格要求）；
- 记忆摘要（`DreamMemoryConsolidator`）默认跳过或降权；
- 日后要升级到 B 时，迁移只需读标记。

另外规格要求"主动回复本身是正常助手台词"——这点现有管线天然满足（回复就是 `OrdinaryChatOutput`）。

### 3.4 用户状态感知（1.5）——**可以做，但规格里的做法比必要的重**

规格给了两套：

**方案一（规格主案）：20s 滑动窗口 + 键鼠量 + 游戏键占比**
- 需要自己轮询 `GetAsyncKeyState`（约 20 个 VK）+ `GetCursorPos` 位移，10Hz；
- 插件已有全局按键轮询的先例（`ChatHotkeyController` 用 `WindowsNativeAPI.GetAsyncKeyState`），技术上没有障碍；
- 但"按键多/游戏键占比"这个分类器的**信息增益很低**：同样是在玩游戏，打字聊天和看视频的差异远比"WASD 占比"明显；而且容易误判（打字写文档会被算成"工作"，但在游戏里打字骂人会被算成"工作"）。
- 隐私上合规（只计数不落盘），但**关闭总开关后必须停掉轮询**。

**方案二（规格备选，也是我建议的主案）：用游戏自带的感知切面**
- `GameForegroundDetector.IsGaming / Loose / ForegroundLowerCached / GamingElapsedSeconds` 已经在做"当前前台是不是游戏/网页/其他"的判定，还带白名单；
- `WindowsNativeAPI.GetLastInputInfo` 直接给"多少秒没动键鼠"；
- 组合成规格里的五态几乎是查表：

| 状态 | 用现有信号近似 | 修正 |
| --- | --- | --- |
| 挂机 | `idle > 120s` 且无前台变化 | −15 |
| 游戏 | `IsGaming == true` 且 `idle < 60s` | +20 |
| 冲浪 | `Loose == true` 或前台进程是浏览器，`idle < 60s` | +10 |
| 工作/学习 | 前台进程是 IDE/Office 等（进程名映射表），`idle < 60s` | −10 |
| 轻度活动 | 其他 | 0 |

**建议**：MVP 只做方案二的粗分（3–5 个状态，不采样键位），把方案一的精细分类列为 P2。
收益差不大，但工作量和误判风险差很多。规格里"平台无法获取输入活动时按中性处理"这条，在方案二下天然满足。

### 3.5 到点提醒（1.2 第 2 步、1.7）——**语义冲突，需要你拍板**

技术实现反而简单：游戏自带 `AlarmSystem`（`AlarmSaveFired` 事件、`TryGetAlarmTime`）和 `MemoReminderSystem`（`Notify`/`IsDue`），
订阅/轮询即可，不用自己存提醒。**难的是规则冲突**：

1. 规格 1.2 第 2 步：提醒**优先于**总开关判断（"到点提醒 → 立即投放，本轮结束"在总开关检查之前）。
2. 规格 1.3：总开关关闭后"不感知、不截屏、不主动说话"。
3. 规格 1.2 第 1 步：剧情播放中"本轮完全跳过（**包括提醒**）"。

→ 于是"总开关关闭但仍然为闹钟说话"会和隐私承诺冲突；"剧情播放中跳过提醒"又会让闹钟失效。
**建议**：
- 提醒单独一个开关（默认关或跟随总开关），文档里写清"提醒不受主动频率限制，但受总开关/剧情开关控制"；
- 或者把提醒从"主动对话"里拆出去，做成独立功能（更符合用户预期：闹钟是他自己设的，应该可靠）；
- 剧情进行中是否提醒：建议**延迟到剧情结束再补报**（队列方式），而不是直接丢弃。

### 3.6 由头来源：闲聊 / 音乐 / 屏幕

- **闲聊（P0，权重 60）**：直接可用。生成时带上下文摘要即可（现有 `ConversationContextBuilder` 已能取最近 12 轮）。
- **音乐（P1，权重 10）**：两条路
  1. 反射读 `MusicPlayerController._lastPath` / `_trackList` + `MusicTrackAnnouncer._lastAnnouncedPath`，拿到曲名；
  2. 用我们已移植的 `AudioSessionProbe` 只判断"有音频会话在放"，再用前台进程名猜"是不是在听歌"。
  建议先做 2（不需要反射私有字段，也不会因为游戏改版失效），要曲名时再做 1。
- **屏幕（P0 清单里，权重 30，设置页有"窥屏开关/权重"）**：**建议降级**，理由见第四节。

### 3.7 设置页

规格要求三组开关。现有设置页是"反射找到游戏原生 Tab，再注入自建行"（`NativeSpeechLanguageRows`、`NativeHotkeySettingsInjector` 等，每行 60–120 行样板）。
主动对话参数较多（总开关、最大次数、期望间隔、3 个由头开关、3 个权重、状态修正……），全塞进原生行会非常重。

**建议**：
- P0：只暴露 3 个控件（总开关、期望间隔、最大次数），其余走 JSON 配置文件（`local.just_lilith.proactive.json`），在原版里这些参数本来也是走 BepInEx 配置的（`ambient_*` 键）；
- P1：再补"由头开关/权重"和"当前状态：游戏，+20"的只读回显；
- 兴趣值反推结果按规格要求回显（"每轮增长约 5–10 点"）。

## 四、难度过大 / 建议砍掉或改写的需求

### 4.1 屏幕内容由头（窥屏）——建议降级

规格写的是"屏幕内容"作为由头。真正做要：截屏 → OCR/视觉模型理解 → 生成由头。问题：

- 隐私：桌面截图含全部窗口内容，比"键鼠计数"敏感一个数量级；
- 成本：每 30s 一次视觉调用，费用与延迟都不可控；
- 效果：本地截图 + 通用视觉模型对"用户在干什么"的判断经常出错，说错话比不说更糟；
- 依赖：当前模型通道是 OpenAI 兼容的 Chat/Responses（文本），没有多模态链路。

**建议改成**：
- 用 `GameForegroundDetector` + 前台窗口标题/进程名（纯文本）作为"用户在做什么"的由头，例如"他在写代码/在浏览器里"；
- 或者干脆挂到游戏自带的 `ScreenshotModeWatcher`（用户主动截图/进入窥屏模式）事件上——用户已经"允许你看"的时候才用，隐私风险大幅下降。
- 如果以后确实要图，建议做成显式开关 + 单张低分辨率 + 只在用户触发动作时（不是定时）截。

### 4.2 键鼠精细分类（20s 窗口 + 按键量 + 游戏键占比）——建议 P2

技术上能做（`GetAsyncKeyState` 轮询插件已经在用），但：
- 误判率高（见 3.4）；
- 需要持续轮询，耗电/CPU 都比 `GetLastInputInfo` 高；
- 关闭开关后必须停轮询，容易漏。

**建议**：先上 3.4 方案二，把"精细分类"作为 P2 迭代，用配置开关控制。

### 4.3 到点提醒与总开关/剧情的语义冲突——必须由你定义

见 3.5。不是技术难点，但**三份规则互相矛盾**，实现前必须选一种，否则每种选择都会让一半验收场景过不了。

### 4.4 "系统旁白不进入历史"与现有成对结构——中等难度，可绕

见 3.3。用方案 A（旁白 + 标记）成本低，但要注意：
- 气泡/记忆/统计三处都要尊重 `ambient` 标记；
- 旧会话文件（`SchemaVersion=3`）不需要迁移。

### 4.5 兴趣值"越到后面越克制"按规格不成立（需要改算法）

见 3.1 的模拟对照：只降上限时三次间隔几乎相同（298/297/298s）。
建议概率乘 `(N−count)/N` 或让增量随次数衰减，否则验收场景 2 的"越来越难触发"没法通过。

### 4.6 与"逐段语音对齐"的天然冲突（规格没写，但会影响体验）

我们刚把 TTS 改成"每段合成好才显示该段文字"。主动对话**首次开口**要等：
LLM 生成（3–10s）→ 第一段合成（5–8s）→ 才出现文字和声音。用户什么都没做，突然等 15 秒才开口，观感会差。

**建议**（也是原版的做法）：主动台词**预生成 + 预合成**——在"暂存"阶段就把文字和音频做好，
轮到时立刻出声；这样主动对话几乎是零延迟，也避开了第七节的流水线问题。

## 七、TTS 流水线：消息队列能解决吗？

### 7.1 现状（先看数据）

我们目前的流程是严格串行的：

```
合成第 N 段 → 等它回来（5–9s）→ 显示第 N 段文字 → 播放第 N 段（6–15s）
→ 播放结束 → 才开始合成第 N+1 段 → …
```

真机日志（`tts/logs/managed-service.log`）：

```
JLTIME chars=38 syn=8.72s audio=9.20s rtf=0.95
JLTIME chars=33 syn=5.30s audio=8.80s rtf=0.60
JLTIME chars=39 syn=5.25s audio=9.27s rtf=0.57
JLTIME chars=61 syn=6.78s audio=15.43s rtf=0.44
```

一段 8 段的回复：音频合计约 **75s**，合成合计约 **45–60s**，其中**约 40–50s 是"播放完了在等合成"的空档**。
这就是你感觉"慢"的来源——不是合成慢，是**串行等待**。

### 7.2 为什么"消息队列"本身没用

队列只是解耦生产者和消费者；如果生产者（合成）一次只做一段，消费者（播放）还是要等它。
真正省时间的是**预取**：在播放下一条之前，就把下一条（或下两条）合成好放在队列里。
所以答案是：**用队列，但关键是队列的"深度≥1 的预取"，而不是队列本身。**

### 7.3 服务端约束（很重要）

`BepInEx/plugins/Just_Lilith/tts/service.py`：

```python
self.slots = threading.BoundedSemaphore(2)   # 一个在跑 + 一个在排队
self.inference_lock = threading.Lock()
```

- 推理是**串行**的，并行发 3 个请求不会更快，只会排队；
- 但允许"1 个在跑 + 1 个排队"，所以**客户端预取深度 = 1 是安全且有效的**（当前段在播时，下一段已在服务端跑或排队）；
- 深度 >1 不会更快，还会挤占首段合成。

### 7.4 方案对比

| 方案 | 做法 | 预期效果 | 代价/风险 |
| --- | --- | --- | --- |
| **A. 客户端预取队列（推荐）** | 生产者任务按顺序合成 N、N+1…；消费者只播放已就绪且已显示的那段；深度 1（可配置 2） | 空档从 ~40–50s 降到 **接近 0**（仅剩"合成比音频长"的少数情况，如 8.72s vs 9.2s 时仍有 ~0） | 需要把 `MainThreadSpeechController` 的单 Task 状态机改成"合成队列 + 播放游标"；取消逻辑要一起改 |
| B. 整段一次合成（回到原版） | 如 ext.60 的 `SynthesizeAsync`：整段文本一次请求，服务端内部会分句 | 少一次往返，仍是串行合成，总时长差不多 | 丢掉"逐段对齐显示"（你刚提的需求），**不建议回退** |
| C. 服务端并行 | 多线程推理 | 无 | `inference_lock` 串行；GPU 显存也不支持 |
| D. 复用连接 | 现在每段 `new LocalTtsClient`（内部 `new HttpClient`）；改为整条消息复用一个 client | 每段省 1–5ms（本机），**收益很小但零风险** | 顺手做 |
| E. 预合成缓存（原版做法） | 把要说的文本提前合成并落盘，播放时直接读 PCM | 主动对话接近零延迟；重复台词（反应音、开场白）命中缓存 | 需要缓存目录与失效策略；不适合一次性文本 |
| F. 调整切片粒度 | 现在 `MaxChunkSpeakable=56`，改成 80–100 | 段数减少 → 往返减少、等待减少 | 文字粒度变粗，且首段更慢；建议只调"首段更小、后续更大"的不对称策略 |
| G. 流式 LLM + 边生成边合成 | 模型边吐字边分段合成 | 首个字出现时间从 ~10–15s 降到 5–8s | 改动大（OpenAI 兼容流式 + 句切分 + 与气泡对齐），建议后续再做 |

### 7.5 推荐组合与预期

1. **A（预取深度 1）**：省掉几乎全部段间空档；
2. **D（连接复用）**：顺手；
3. **E（主动对话预合成）**：主动台词零延迟；
4. **F（首段更小，≤20–24 字）**：首字出现更快，代价是首段音频短、衔接更多——需要真机听感验证。

按 8 段、75s 音频的样例估算：串行 ≈ 120–135s，预取后 ≈ **80–90s**（只受音频长度约束），
**整体缩短约 30–35%**；如果连 LLM 首字延迟也算进去，感知提升更明显（用户不再每段等 5–9 秒）。

### 7.6 实现要点（给下一个窗口）

- 把 `_active`（单个合成 Task）换成"生产者循环 + `ConcurrentQueue<ChunkResult>`"，深度用 `SemaphoreSlim(depth)` 控制背压；
- 播放仍由主线程 `Update` 驱动，条件从"有 `_readyWave`"改为"队列非空且段号 == 当前显示段号"；
- **文字仍然只在对应音频就绪后显示**（保持你这次的需求）；
- 取消：`RequestStop`/用户新消息时，取消生产者 token 并清空队列；
- 失败降级：某段合成失败 → 跳过该段文字？还是整条回退整段文字？建议"该段静默跳过、继续后续段"，并在日志里标 `chunk_failed`；
- 超时：单段 30s 超时（服务端有 180s，客户端可以更短）；
- 主动对话走"预合成"路径时，直接命中缓存，不经过生产者。
