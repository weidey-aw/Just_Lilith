# 主动对话 & 窥屏对话：需求整理与可行性分析（v2）

> 本版按最新决策重构：**两个功能拆开**（主动对话 / 窥屏对话），并把 **TTS 对话提速** 单独成章。
> 适用范围：`D:\Code\Just_Lilith`（0.3.0 裁剪版源码）。
> 参考：`_decomp/`（原版 `0.3.0-ext.60` 反编译）与游戏本体 `Assembly-CSharp` 公开 API。
> 本文只做整理与分析，不含代码改动。

---

## 0. 本版决策记录（相对上一版的取舍）

| 决策 | 结论 | 影响 |
| --- | --- | --- |
| 闹钟 / 到点提醒 | **不做** | 原 P0 里"检查到点提醒"整条移除；`AlarmSystem`/`MemoReminderSystem` 不接入 |
| 用户状态感知 | **直接用游戏本体已有的判定** | 不采样键鼠、不做"游戏键占比"分类器；见 1.4 |
| 系统旁白 | **不做** | 不新增可展示/可统计/可持久化的"系统旁白"数据类型；主动对话的触发指令只在**当次请求内**生效（口径见 1.5，与窥屏规格的冲突见 Q1） |
| TTS 对话提速 | **要做** | 方案见第 5 章（预取流水线为主） |
| 功能边界 | **主动对话、窥屏对话拆成两个功能** | 窥屏没有独立定时器，依附主动对话的节流与投放闸门 |

**一句话结论**：两个功能都做得到。工作量集中在三块——主动对话服务、窥屏的多模态请求路径、TTS 流水线；
真正需要额外投入的是**原生多模态请求**（现有客户端是纯文本），其余都是在本仓库已有地基上加装。

## 1. 功能一：主动对话

### 1.1 目标与边界

用户长时间不互动时，角色自己找由头说一轮；有分寸（不打断对话/输入、不刷屏、越后越克制）、有理由、与普通回复同质（进历史，用户可直接接着聊）。

**不包含**：到点提醒、固定日程问候、多角色轮换；不保证每次触发都说出口（暂存/过期/放弃都是设计的一部分）。

### 1.2 触发与节奏：兴趣值

规则（沿用规格 1.4）：`0..100`，`≤50` 不触发，`>50` 按 `clamp((兴趣 + 状态修正 − 50)/50, 0, 1)` 掷骰；生成即清零、次数 +1；用户发消息则三者重置。

**默认值必须用数值模拟定，不能用线性直觉。** 本次用蒙特卡洛（6000–8000 次）算出：

| 每轮增量均值 | 首次触发平均轮数 | ≈ 时间（30s/轮） |
| --- | --- | --- |
| 3 点 | 21.5 轮 | 645s |
| 5.25 点 | 13.1 轮 | 392s |
| **7.2 点（增量 U(4.8, 9.6)）** | **9.6 轮** | **287s** |
| 7.5 点 | 9.6 轮 | 287s |

→ 默认增量取 **U(4.8, 9.6)**（约 5–10 点/轮，与规格描述一致）；程序保留二分法，用户改"期望间隔"后自动重算，设置页回显"每轮增长约 X–Y 点 / 约 N 分钟开口一次"。

**⚠️ 规格缺陷：只降"兴趣上限"不会让后面更难。** 概率只看 `(兴趣−50)/50`，兴趣每次触发后清零重爬，上限 100→83→67→50 基本碰不到。模拟对照（三次触发间隔）：

| 衰减方式 | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 规格原样（只降上限） | 298s | 297s | 298s |
| **建议：概率再乘 `(N−count)/N`** | 298s | 319s | 374s |

**实现建议**：概率乘 `max(0.15, (N−count)/N)`；不想偏规格就把"越来越难"从验收里删掉（见 Q2）。

### 1.3 由头与暂存

```
每 30s（剧情播放中直接跳过整轮）：
  if !总开关: return
  处理外部请求队列（音乐变化等）→ 尝试投放
  清理过期暂存 → 按优先级尝试投放 1 个
  if 兴趣掷骰命中:
      生成由头（LLM 一次性指令，不落历史）→ 尝试投放
投不进去（输入中 / 生成中 / 说话中 / 气泡未清）→ 暂存（带 expiresAt）
暂存过期 → 丢弃，不补说、不报错
```

投放闸门的现成信号：

| 判定 | 信号 |
| --- | --- |
| 用户正在输入 | `LlmConfigurationView._chatInput.isFocused`（或 `AnySettingsFieldFocused`） |
| 正在生成 | `LlmConfigurationController._chatBusy`（与聊天共用同一把锁） |
| 正在说话/排队 | `MainThreadSpeechController.SpeechActive` |
| 气泡未清 | `LlmGameBridge.IsConversationActive` |
| 剧情播放中 | `DialogueManager.IsOnceStoryPerforming` |

### 1.4 用户状态感知：只用游戏本体已有的

**不采样键鼠、不读窗口标题、不读剪贴板。** 只读游戏已经算好的量：

| 信号 | 游戏 API | 用途 |
| --- | --- | --- |
| 距上次输入多少秒 | `WindowsNativeAPI.GetLastInputInfo(ref LASTINPUTINFO)` | 挂机判定（>120s） |
| 是否在玩游戏 | `GameForegroundDetector.IsGaming` / `Loose` | 游戏 +20 / 冲浪 +10 |
| 连续游戏时长 | `GameForegroundDetector.GamingElapsedSeconds` | 玩得久时更积极 |
| 前后台切换 | `GameForegroundDetector.ForegroundLowerCached` 变化 | "刚切走/切回"事件由头 |

状态映射（建议值，均可配置）：

| 状态 | 判定 | 修正 |
| --- | --- | --- |
| 挂机 | `idle > 120s` | −15 |
| 游戏 | `IsGaming && idle < 60s` | +20 |
| 冲浪 | `Loose && idle < 60s` | +10 |
| 轻度活动 | 其他 | 0 |

> 游戏内部可能用窗口标题做判定，但**我们只读它输出的布尔量**，不自己采集标题，符合"不做窗口标题采集"的非目标。

### 1.5 生成与历史：没有"系统旁白"

**口径（本版定义）**：不做旁白数据 —— 触发信息只以"当次请求的临时指令"进入 prompt，**不写入历史、不展示、不参与统计与记忆**。

- 生成前点亮"思考中"；放弃/暂存必须熄灭（`LlmGameBridge.ShowThinking/EndThinking`）。
- 与聊天共用 `_chatBusy`：锁被占用 → 本轮放弃，下一轮再试。
- 失败/未配置 → 安静跳过，不弹窗。
- **历史落库**：主动回复是正常 assistant 台词，但**没有对应的 user 轮次**。需要把 `ConversationTurn(User, Assistant)` 扩成允许"仅 assistant"：
  - 推荐：`ConversationTurn` 增加 `bool IsAmbient`，`User` 允许空；上下文构建时把这类轮次渲染成"（她主动说的）"前缀，避免模型以为用户在说话；
  - 旧会话文件（`SchemaVersion=3`）无需迁移（新字段有默认值）。
- 记忆摘要（`DreamMemoryConsolidator`）默认跳过 `IsAmbient` 轮次。

### 1.6 设置项

P0 只暴露 3 个：**总开关（默认关）**、**期望间隔（1–60 分钟，默认 5）**、**用户回应前最大次数（默认 3）**。
其余（由头开关/权重、状态修正、暂存寿命）走 JSON：`BepInEx/config/local.just_lilith.proactive.json`，设置页只做只读回显。

### 1.7 验收

| 场景 | 满足方式 |
| --- | --- |
| 关闭总开关 → 永不开口 | `enabled=false` 时 tick 直接 return，且不读状态、不启动任何感知 |
| 5 分钟 → 最多 3 次、越来越难 | 兴趣模型 + 概率递减（见 1.2） |
| 用户发一句 → 重置 | `NotifyUserMessage()` 清兴趣/次数/恢复上限 |
| 输入中 → 拦下并暂存 → 之后补投 | 投放闸门返回 false → 暂存；条件恢复后补投 |
| 兴趣触发但暂存超时 → 不补、不报错 | 过期丢弃 |
| 模型未配置 → 静默 | 复用现有 `IsConfigured` 检查 |

### 1.8 可行性与工作量

| 模块 | 行数 | 说明 |
| --- | --- | --- |
| `ProactiveSettings` + Store | ~180 | 仿 `FoundationOptionsStore` |
| `InterestModel`（含反推） | ~120 | 纯 Core，可单测 |
| `StagedCueQueue` | ~100 | |
| `ProactiveContextProbe`（读游戏信号） | ~200 | 反射，全部可空 |
| `ProactiveChatService`（tick/状态机/投放） | ~400 | |
| `SendProactive` + 历史改造 | ~140 | 改 `LlmConfigurationController`、`ConversationTurn`、`ConversationContextBuilder` |
| 设置页 3 项 | ~250 | 原生行样板 |
| **合计** | **~1400 行** | **2.5–3.5 人日** |

## 2. 功能二：窥屏对话（P1）

### 2.1 目标与边界

角色偶尔"瞥一眼"桌面，并据此自然地开启话题；观感是"旁边的人看了一眼"，不是念屏幕。
**不做**：持续截屏/录屏、OCR、读窗口标题、读剪贴板/文件、监听输入。

### 2.2 触发

- **没有独立定时器**：完全依附主动对话的节流（30s 检查、兴趣值、投放闸门、暂存）。
- 只有加权随机抽中"屏幕"由头时才截屏一次。
- 两个开关：**窥屏开关**、**窥屏权重**；总开关关闭 → 绝不截屏。
- 截屏要快；识图可能数秒，期间保持"思考中"。

### 2.3 截图链路（技术可行性已核实）

**结论：可行，但有三点要注意（编码库、窗口污染、多屏）。**

| 环节 | 方案 | 依据 |
| --- | --- | --- |
| 抓屏 | 自写 P/Invoke：`GetDC(IntPtr.Zero)` + `StretchBlt` 到 1024×768 的 32bpp DIB | 游戏 `WindowsNativeAPI` 没有 BitBlt/GetDC，需自带声明；仓库已有 P/Invoke 先例（`WindowsSecretProtector`、`TtsServiceManagerProcess`） |
| 多显示器 | 用 `LilithWindow.VirtualScreen`（游戏已算好的虚拟桌面矩形）作为源区域 | 避免自己调 `GetSystemMetrics` |
| 编码 | **不能用 System.Drawing.Common**（游戏 `dotnet/` 只有 `System.Drawing.dll` 门面，没有 `System.Drawing.Common.dll`）；改用 Unity 的 `ImageConversionModule`：像素 → `Texture2D.LoadRawTextureData` → `ImageConversion.EncodeToJPG(quality)` | `BepInEx/interop/UnityEngine.ImageConversionModule.dll` 存在（11,264 字节），csproj 加一条引用即可 |
| 体积 | 1024×768 JPEG q≈70 → 约 80–150KB，base64 后约 110–200KB；视觉 token 约 1k 量级 | 符合"千 token 量级" |
| 耗时 | GDI 抓屏+缩放 <20ms，JPEG 编码 10–30ms | 可接受 |
| **窗口污染** | 气泡/聊天框都在游戏那个**分层窗口**里；`BitBlt`/`StretchBlt` **不带 `CAPTUREBLT` 时通常不包含分层窗口**，正好排除她自己的 UI | 需真机验证；若仍拍到：① 截屏前 1 帧隐藏 UI（有闪烁）② 交给视觉模型忽略 |

隐私：截图只在内存中存在，用完即弃；不落盘、不进日志、不进记忆。

### 2.4 理解屏幕：两种方式

| | 方式 A：原生多模态 | 方式 B：旁白转述 |
| --- | --- | --- |
| 适用 | 对话模型本身支持图片，且"用户允许原生识图"或"视觉模型就是对话模型" | 不满足 A，或原生编码失败 |
| 请求 | 本轮请求附图片，**只此一轮可见**，不写历史/记忆 | 截图先发给视觉模型，要 200 字以内第三人称描述，再作为本轮提示 |
| 历史 | 不留图片（按本版口径也不留提示文本，见 Q1） | 按规格应留 ≤200 字描述（与本版"不做旁白"冲突，见 Q1） |
| 失败 | 原生编码失败 → 转 B | 超时/空 → 本轮窥屏作废，按 2.5 降级 |

**方式 A 的真实成本（已核实）**：现有 `ChatMessage(ChatRole, string Content)` 是纯文本，`OpenAiCompatibleClient` 把消息序列化成 `List<Dictionary<string,string>>` + `["content"] = string`。要发图必须**新增一条多模态请求路径**：

- Chat Completions：`content: [{type:"text"}, {type:"image_url", image_url:{url:"data:image/jpeg;base64,..."}}]`
- Responses：`input` 里用 `input_image`
- 需要一个"是否视觉模型"的能力标记（模型目录不提供），由用户勾选或指定"视觉配置 = 第 N 套配置"
- 代码量：Core 里加一个多模态消息模型 + 两条协议的序列化分支，约 150–250 行

**方式 B 的成本**：复用现有文本客户端，只需 ① 一个"视觉配置"（URL/Key/模型，可指向三套配置之一或单独填）；② 一段固定的转述 prompt。约 80–120 行 + 100 行配置/UI。

**建议**：先做 **B**（低风险，1.5–2 人日跑通），A 作为第二阶段（要改两条协议）。

### 2.5 选择与降级（同一处判定）

```
抽中"屏幕"由头 →
  if !窥屏开关 || !总开关: 走普通由头
  if 截屏失败: 降级
  if 原生可用(配置了支持图片的模型 && 允许原生): 方式A
     └ 编码失败 → 尝试 B
  else: 方式B（需要视觉配置）
       └ 无视觉配置/超时/空 → 降级
降级 = 闲聊由头开着 → 退化成普通话题；闲聊也关 → 本轮不开口（兴趣已消耗，不补偿）
全程不弹错误框、不往 UI 刷错误
```

### 2.6 表达约束（写进系统提示的固定片段）

- 自然口语，只挑最在意的一点说，不逐条念画面；
- 不主动说出账号/密码/私聊/他人姓名等隐私；
- 不把屏幕内容当成用户发言；
- 不描述自己的对话框与立绘；
- 画面没东西可说 → 可以不说，或轻轻带过。

### 2.7 隐私与权限

- 设置里一键关闭；关闭后不再调用截屏接口。
- 首次开启主动对话/窥屏时弹一次说明："会截取桌面画面并发送给你配置的模型"。
- 只发给用户自己配置的对话/视觉模型，不发其他服务。
- 不持久化截图、不写记忆、不写日志。
- 只截屏：不读窗口标题、不读剪贴板、不读文件、不录屏。

### 2.8 验收

| 场景 | 满足方式 |
| --- | --- |
| 抽中屏幕由头 → 回复与画面相关 | 方式 A/B 二选一 |
| 原生模式 → 请求带图、历史无图 | 图片只在本轮请求 |
| 转述模式 → 历史出现 ≤200 字描述 | **取决于 Q1**（本版口径不落历史） |
| 关闭窥屏 → 不再截屏，其他由头正常 | 开头短路 |
| 未配置视觉模型 → 降级普通话题、不报错 | 2.5 决策树 |
| 截屏失败 → 本轮不开口，其他轮不受影响 | 同上 |
| 截图含本应用窗口 → 不描述自己 | 提示约束 +（可选）CAPTUREBLT 排除 |

### 2.9 可行性与工作量

| 模块 | 行数 | 风险 |
| --- | --- | --- |
| 抓屏 + 缩放 + JPEG（P/Invoke + ImageConversion） | 200 | 中：多屏/DPI/分层窗口是否被拍到，需真机验证 |
| 视觉配置（复用三套配置之一 / 单独填） | 120 | 低 |
| 方式 B 转述（prompt + 调用） | 100 | 低 |
| 方式 A 多模态请求（两条协议） | 150–250 | **中偏高：要改客户端核心序列化** |
| 投放/降级接线 | 80 | 低 |
| **合计（B 优先）** | **~500 行 / 1.5–2 人日** | A 再加 **1–1.5 人日** |

## 5. TTS 对话提速方案（要做）

### 5.1 现状与实测

现在（逐段对齐版本）是**严格串行**：

```
合成第 N 段（5–9s） → 显示第 N 段文字 → 播放（6–15s） → 播放完 → 才开始合成第 N+1 段
```

真机样本（`tts/logs/managed-service.log` 的 `JLTIME`）：

```
chars=38 syn=8.72s audio=9.20s rtf=0.95
chars=33 syn=5.30s audio=8.80s rtf=0.60
chars=39 syn=5.25s audio=9.27s rtf=0.57
chars=61 syn=6.78s audio=15.43s rtf=0.44
```

一次 8 段回复实测：音频合计 **74.9s**，合成合计约 **48–55s**，其中**约 40–50s 是"播完了在等合成"**。
**不是合成慢，是串行等待。**

### 5.2 服务端约束（决定并行没用）

`BepInEx/plugins/Just_Lilith/tts/service.py`：

```python
self.slots = threading.BoundedSemaphore(2)   # 一个在跑 + 一个在排队
self.inference_lock = threading.Lock()       # 推理串行
```

- 并行发 N 个请求不会更快，只会排队；挤掉首段反而更慢。
- 允许"1 个在跑 + 1 个排队" → **客户端预取深度 = 1 是安全且有效的上限**。

### 5.3 候选方案对比

| 方案 | 做法 | 收益 | 代价/结论 |
| --- | --- | --- | --- |
| **A. 预取流水线** | 播放第 N 段时，生产者已合成第 N+1 段（深度 1） | 空档 ≈ `Σmax(0, syn−audio)`，样本估算省 **30–35%** | 需把控制器单 Task 改成队列 + 游标；1–1.5 人日 |
| B. 整段一次合成 | 一次请求整段，服务端内部按句合成后拼接（原版 ext.60 做法） | 往返少、无段间空档 | **首段等待 = 整段合成时间（≈50s）**，且丢掉逐段文字对齐 → 不采用 |
| C. 并行合成多段 | 客户端并发 | 无 | 服务端串行 + slot=2，反而更慢 |
| D. 连接复用 | 现在每段 `new LocalTtsClient`（每段新建 `HttpClient`）；改为整条消息复用一个 client | 每段省 5–20ms，减少抖动 | 低风险，顺手做 |
| E. 预合成缓存 | 主动/窥屏台词在"暂存"阶段就合成好；固定台词落盘缓存（`tts/cache` 已有目录） | 主动开口接近 0 延迟 | 需要文本 hash 缓存键与失效策略 |
| F. 首段小切片 | 首段 ≤20–24 字，后续 56 字 | 首字提前 2–4s | 段数 +1，听感要验 |
| G. 流式 LLM + 边生成边合成 | 模型边吐字、按句切分提前合成 | 首字从 ~10–15s 降到 5–8s | 改动大，列第二阶段 |

### 5.4 推荐方案

**A（预取深度 1） + D（连接复用） + E（主动台词预合成）**，F 作为可调项，G 留到以后。

```
                ┌──────────── 生产者（后台线程）────────────┐
  文本分段 ──▶  │ 串行合成 chunk0,1,2…（复用同一个 client） │ ──▶ Ready 队列（≤2 段）
                └──────────────────────────────────────────┘
                                    │ 有就绪段 & 播放器空闲
                                    ▼
                    主线程：显示该段文字 → 播放该段 → 等播放结束
```

关键点：
- **文字仍然只在对应音频就绪后显示**（保住上一轮需求）；
- 生产者可以领先播放器 `ahead` 段（默认 1，可配 2）；
- Ready 队列有界（≤2 段；48k/16bit/单声道 15s ≈ 1.4MB/段，最多 ~3MB）；
- 取消：用户新消息 / 关闭 TTS / 退出 → 取消生产者、清队列、停音频；
- 单段失败：记 `chunk_failed` 并跳过该段，不打断后续；可选"整条回退整段文字"。

### 5.5 改造点（文件级）

| 文件 | 改动 |
| --- | --- |
| `Unity/Speech/SpeechPipeline.cs`（新增） | `ChunkPlan`、生产者循环、`ConcurrentQueue<ChunkAudio>`、`CancellationToken`、`ReadyCount` |
| `Unity/Speech/MainThreadSpeechController.cs` | `_active`/`_readyWave` 换成 pipeline；播放结束 → 取下一段就绪；状态文案改"第 N/M 段" |

| 主动对话服务 | 生成时把台词预合成进缓存（E） |

### 5.6 预期收益（按 8 段样本推算）

| 方案 | 总时长 | 说明 |
| --- | --- | --- |
| 现状 | ≈ 75s（音频） + 50s（串行合成） ≈ **125s** | 段间平均 6s 空档 |
| A | ≈ 75 + 首段 6 + 溢出 ≈ **85–90s** | 空档只剩"合成比前段音频长"的部分（样本约 2–3 段，合计 5–8s） |
| A + D + F | ≈ **80–85s**，首字再提前 2–4s | |
| 加 E（主动对话） | 主动台词 ≈ 0 等待 | 缓存命中 |

**整体缩短约 30–35%**，"每段说完停 5–9 秒"的观感会消失大半。

### 5.7 风险

1. **分片与播放对不齐**：必须"段号 + 就绪"双条件，避免提前播放未显示的段；
2. **取消/打断**：新消息进来要立刻清队列，否则旧段会冒在新回复后面；
3. **内存**：Ready 队列不设上限会堆积（8 段 ≈ 11MB），必须 ≤2；
4. **失败语义**：跳段后文字与音频少一句，需日志可定位（`chunk_failed`），UI 不弹错误。

### 5.8 分阶段落地

| 阶段 | 内容 | 工期 | 收益 |
| --- | --- | --- | --- |
| 1 | D 连接复用 + F 首段小切片 | 0.5 人日 | 首字更快、抖动更小 |
| 2 | A 预取流水线 | 1–1.5 人日 | **主要收益（30%+）** |
| 3 | E 主动台词预合成 | 0.5 人日 | 主动/窥屏零延迟 |
| 4（可选） | G 流式 LLM | 2–3 人日 | 首字再降 |
